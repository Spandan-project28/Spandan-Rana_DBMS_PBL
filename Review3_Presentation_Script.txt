2. PROBLEM STATEMENT (60-75 sec)
-------------------------------------------------------------------
"Before going further — why is this a hard database problem, not a
simple 'book a seat' app?

1. The SAME seat can be sold to multiple passengers on the same train
   and date, as long as their station-to-station segments don't
   overlap — e.g. Delhi→Kanpur and Kanpur→Patna on the same seat. A
   plain booked/not-booked flag can't model that; we need segment-
   level, interval-overlap logic.
2. When no compatible seat is free, the passenger is waitlisted FIFO —
   but the system still has to remember which class and which route
   they wanted, so promotion later assigns the right seat, not just any
   seat.
3. Refunds are tiered by how close to departure you cancel, and the
   refund actually paid must be stored permanently — not re-guessed
   later from a clock that has since moved on.
4. Deleting a train, station, or passenger that already has booking
   history must be blocked with a clear error, never silently
   cascaded away.
5. Two passengers requesting the same seat-segment at the same instant
   must not both succeed.
6. And the final deliverable has to be a real application doing real
   CRUD and search against a live database — not a UI simulating
   itself with in-memory JavaScript arrays, which is exactly what
   Review 3 replaces."

-------------------------------------------------------------------
3. SOLUTION / ARCHITECTURE (45 sec)
-------------------------------------------------------------------
"Our solution is three layers: a MySQL database (RailwayReservationDB)
with 11 normalized tables — Station, Train, Route_Stop, Schedule,
Coach, Seat, Passenger, Booking, Journey_Segment, Waitlist, Payment —
all in 3NF with primary keys, foreign keys, unique, check and default
constraints, plus indexes on the columns we search by most.

In the middle, a Python Flask backend: app.py exposes the REST API,
and booking_service.py holds all the business logic — search, segment-
aware seat allocation, fare calculation, cancellation, and promotion.

On top, this same UI you're looking at — unchanged pixel-for-pixel from
earlier reviews — but its JavaScript now calls real API endpoints
instead of reading a mock array.

The core rule — no overlapping seat segments — is enforced twice: once
in booking_service.py during the booking transaction, and again as a
database trigger, trg_prevent_seat_segment_overlap, as a safety net."

7. ANTICIPATED QUESTIONS — QUICK ANSWERS
-------------------------------------------------------------------
Q: Why ON DELETE RESTRICT instead of CASCADE?
A: Cascade would silently destroy booking/payment history when a train
   or passenger is deleted. RESTRICT blocks it with a 409 instead.

Q: How do you stop two people double-booking the same seat-segment at
   once?
A: The booking transaction checks-then-inserts inside one transaction,
   and the trigger re-validates at insert time as a second line of
   defense. (Noted limitation: a SELECT ... FOR UPDATE row lock would
   close the remaining tiny race window further under very high
   concurrency — documented as future work, not hidden.)

Q: Where exactly is "no overlapping segments" enforced?
A: Twice — in backend/booking_service.py during the booking logic, and
   again in the database via trg_prevent_seat_segment_overlap.

Q: Is the UI just a redesigned mock?
A: No — app.html is visually the same as earlier reviews, but every
   button now calls a real Flask API endpoint backed by live MySQL.
   Every search, booking, cancellation, and report shown is a genuine
   database operation.

Q: What happens to a waitlisted passenger's seat class/route preference?
A: It's stored on the Waitlist row itself (requested coach, source and
   destination route stop), so promotion later assigns exactly what
   they originally asked for, not an arbitrary seat.
